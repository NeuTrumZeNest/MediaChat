# Личные переписки MediaChat

## Устройство

Используются существующие `Conversation`, `ConversationMember` и `Message.conversationId`.
`null` обозначает общий чат. У личного диалога ровно два участника; маршрут создания
не принимает список участников и не создаёт группы.

`Conversation.directKey` — уникальная строка `min(userId):max(userId)`.
Создание выполняется транзакцией: advisory lock пары → поиск существующего диалога →
проверка пользователя → создание диалога и двух участников. Уникальное ограничение
PostgreSQL дополнительно защищает от дубликатов. Создание с собой запрещено.
На момент аудита таблица диалогов была пустой, перенос старых переписок не требовался.

Миграция `20261116T1009_direct_conversations` добавляет только nullable-поле,
уникальное ограничение и индекс сообщений `(conversationId, id)`. Предыдущий контракт:
`6612279b903bd02d12716743678cb6e73ba90d6a48fca3677288cf5441a68c67`.
Новый контракт: `ec313e38c603aa40dcd2fa5b502176f554a9ae2500eecfa28a314c259008f9d3`.
DDL проверен, миграция применена штатным Prisma 8 `db migrate`, сброс не используется.
На другой БД сначала выполнить `prisma db verify --json`, проверить историю/DDL и
только затем применить подходящий путь миграций. Классические Prisma 7 команды не подходят.

## API и интерфейс

- `GET /api/users?q=имя`: до 30 совпадений, только `id`/`username`, текущий пользователь исключён.
- `POST /api/conversations`, JSON `{userId}`: создать либо вернуть единственный личный диалог.
- `GET /api/conversations`: диалоги текущего пользователя, собеседники, последние сообщения,
  время и сортировка активности. Связи загружаются через relation includes, без цикла запросов по собеседникам.
- `GET /api/messages?conversationId=ID&before=ID`: история по 50 сообщений,
  строгий курсор по уникальному `id`, `nextCursor`/`hasMore`. Без conversationId — общий чат.

Выбор чата сохраняется в `?chat=ID`. При смене ключа React создаёт отдельное состояние
чата: сообщения, ответы, меню, редактор и галерея предыдущего диалога не переносятся.
Черновики текста/файлов сохраняются в памяти вкладки при обычном переключении.
Во время отправки/повтора неоконченной отправки и сохранения изменений переключение
через список блокируется. Адресат фиксируется в PendingSend до начала загрузок.
После перезагрузки сохраняются выбранный диалог и история, но не несохранённый черновик.
На мобильном экране боковая панель показывает компактные аватарки и кнопку поиска.
Профили используют существующие username и инициалы: загрузки пользовательских аватарок в модели пока нет.

История подгружается кнопкой; позиция прокрутки сохраняется при добавлении старых страниц.
Переход по цитате может последовательно загрузить до 20 страниц той же переписки.
При восстановлении соединения обновляется последнее окно истории; старые страницы можно снова загрузить.

## Socket.IO

JWT проверяется при handshake; сервер определяет автора по cookie, а не по payload.
Каждое подключение входит в `general`, собственную `user:ID` и доступные `conversation:ID`.
`subscribe-conversation` повторно проверяет участие. Подписки восстанавливаются при reconnect.
Срок JWT ограничивает время жизни соединения.

При создании диалога API вызывает зарегистрированный custom server publisher через
`globalThis[Symbol.for(...)]` в том же процессе Node. Он присоединяет уже открытые
сессии двух участников к комнате и посылает `conversations-changed` только им.
Это не внешний брокер и не отдельная архитектура: текущий проект работает одним Node-процессом.

`chat-message`, `message-edited`, `message-deleted` содержат `conversationId`.
Доставка идёт только в соответствующую комнату. Автор получает ACK сохранения;
другие вкладки автора тоже получают событие. Клиент фильтрует события по активному чату
и объединяет сообщения по ID. Уникальный clientMessageId позволяет повторить отправку
после потери ACK без создания дубликата. История не может откатить более свежее realtime-редактирование.

## Доступ к сообщениям и файлам

История, отправка, подписка, редактирование и удаление проверяют участие на сервере.
Правка и удаление дополнительно требуют авторства. Ответ разрешён только на неудалённое
сообщение из той же переписки. Общий чат не видит приватные цитаты.

Выдача изображений/превью/оригиналов, аудио, видео/постеров/Range и документов
переиспользует существующие проверки: владелец либо участник переписки, где опубликован файл.
Чужой UUID/URL сам по себе доступа не даёт. До публикации загрузка доступна только владельцу.
При прикреплении проверяется владелец и отсутствие действующих ссылок на файл в другой
переписке. Проверка и запись выполняются под теми же блокировками медиа, что и очистка.
Для явной отправки того же оригинала другому адресату нужно выбрать файл заново:
создастся отдельный UUID. Сами оригиналы и готовые плееры не изменялись.

Удаление сообщения использует прежнюю очередь MediaCleanupJob: сообщение скрывается у
участников, затем оригинал и производные удаляются, если больше нет действующих ссылок.
Приватные ссылки других сообщений учитываются при очистке так же, как публичные.

## Воспроизводимая проверка

Не запускать интеграционный тест на production. Используется отдельный сервер с
отключённой плановой очисткой, чтобы не затрагивать старые пользовательские uploads:

```sh
PORT=3102 APP_ORIGIN=http://localhost:3102 MEDIA_CHAT_DIST_DIR=.next/direct-check MEDIA_CLEANUP_ENABLED=false npm run dev
# другой терминал
node scripts/verify-direct-messages.mjs
```

Скрипт создаёт три временных аккаунта, только собственные сообщения/диалоги/файлы;
`finally` удаляет только эти фикстуры. Для повторного прогона перезапустить тестовый сервер,
иначе корректно сработает лимит регистрации 5/час. Нужны FFmpeg, Chrome и Playwright Core;
путь к последнему передаётся через `PLAYWRIGHT_MODULE` (по умолчанию временная установка
`/private/tmp/mediachat-direct-browser/node_modules/playwright-core/index.mjs`). Зависимости
приложения не изменяются ради браузерного теста.

Проверяются конкурентное создание A–B/B–A, запреты для C, все четыре типа вложений
в обе стороны, точные байты оригиналов, Range, комнаты/несколько сессий/reconnect,
пагинация без дублей, приватные ответы/редактирование/удаление и интерфейс Chrome.
Фактические результаты последнего прогона записаны в `V1-PROGRESS.md`.

## Ограничения и следующий этап

- Проверка настоящих Safari/iOS и физического телефона остаётся ручной; Chrome проверяет узкую ширину.
- Список переписок пока без пагинации, прочтений, уведомлений, архива и закрепления.
- Один процесс Node: для нескольких workers нужны общий Socket.IO adapter, согласованная
  доставка событий создания и общий rate limiter. Текущий publisher рассчитан на один процесс.
- Перезагрузка страницы не сохраняет локальные File-черновики; обновление соединения
  возвращает последнее окно истории вместо сохранения старой позиции.
- Нет загрузки собственных аватарок, групповых чатов или удаления диалога целиком.
- Следом — отдельная финальная стабилизация и ручная проверка на устройствах, квоты хранения,
  конфигурация reverse proxy/HTTPS/real IP и подготовка закрытой беты. Новые функции не начаты.
